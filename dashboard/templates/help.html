사용법

DAST(동적 애플리케이션 보안 테스트) 도구입니다. 소스 없이 실행 중인 서비스에 요청을 보내 응답으로 판정합니다 — ① 표면 수집 → ② 수집 지점에 패턴 주입 → ③ 응답 판정(취약·잠재·안전) → ④ 보고.
지금 등록된 모듈 {{ counts.modules }}개(범용 {{ counts.general }} · 프로젝트 전용 {{ counts.specific }}), 프로젝트 팩 {{ counts.projects }}개. 자세한 설명은 저장소 README.md.

처음 쓰는 순서

  1. 대상 탭에서 프로젝트를 고르고 주소를 등록합니다. 프로젝트 허용 범위 밖 주소는 등록되지 않습니다.
  2. 위쪽 대상 칸에서 점검할 대상을 고릅니다. 모든 탭이 이 대상 기준으로 바뀝니다.
  3. 모듈 탭에서 표면 수집 모듈을 돌려 엔드포인트·파라미터를 모읍니다.
  4. 표면 탭에서 지점을 골라 지점 점검 모듈을 돌립니다. 지점마다 취약 · 잠재 · 안전이 붙습니다.
  5. 대상 점검 모듈(보안 헤더 등)은 모듈 탭에서 바로 실행합니다. 능동 모듈은 '자체 환경 확인'에 체크해야 실행됩니다.
  6. 결과 탭에서 행을 눌러 근거·조치를 보고 상태(미확인·확인됨·조치됨·오탐)를 정합니다.
  7. ATT&CK·시나리오 탭으로 흐름을 보고, 위쪽 보고서 내려받기로 Markdown 을 받습니다.

결과

  • 요약 카드는 조치됨·오탐을 뺀 수입니다. 카드를 누르면 그 심각도만 봅니다.
  • 심각도·모듈·상태 필터는 고르면 바로 적용됩니다. 검색칸은 지금 표 안에서만 찾습니다.
  • 행을 누르거나 Enter 를 누르면 오른쪽에 상세가 열립니다. 상태는 여기서 바꿉니다.
  • 같은 모듈이 같은 위치에서 같은 걸 다시 찾으면 줄이 늘지 않고 갱신됩니다. 조치됨으로 바꾼 결과가 다시 나오면 미확인으로 돌아갑니다(재발).
  • 경로가 다르면 다른 줄입니다. 보안 헤더를 세 경로에서 돌리면 같은 항목이 경로마다 하나씩 생깁니다.

도구

  • 값을 넣고 바로 결과를 보는 모듈입니다. 표의 이어서 보기를 누르면 그 행의 값으로 다시 돌립니다 — 테이블 목록 → 그 테이블의 컬럼 → 그 컬럼의 값 순으로 눌러 들어갑니다.
  • 한 번 읽은 값은 기억해 둬서 다시 묻지 않습니다. 같은 것을 또 돌리면 요청 0번으로 끝납니다.
  • 찾은 것은 결과 탭에도 쌓이고, 쓴 요청·응답은 요청 기록에 남습니다.
  • 경로 조작은 읽을 경로를 한 줄에 하나씩 넣습니다. 인코딩을 고르면 그 형태로 바꿔 보냅니다 (새싹에듀에서는 %25%32%65… 형태가 통합니다 — ../ 를 지운 뒤에 디코딩하는 순서라서).
  • SQL 주입은 ①주입되는지 확인(요청 2번)부터 하고, 된 다음에 ②테이블 → ③컬럼 → ④값으로 갑니다. 한 글자씩 묻는 방식이라 느립니다 — 이름 하나에 100번쯤 듭니다. 몇 개씩만 끊어 읽으세요.

역할 — 같은 프로젝트 안에 서버가 여럿일 때

  • 한 프로젝트에 사용자 웹·관리자 웹·Wazuh 가 같이 있고, 터널로 열면 셋 다 localhost 로 보입니다. 그래서 대상마다 역할을 골라 둡니다.
  • 모듈은 자기가 맞는 역할을 정해 둡니다. 안 맞는 대상에서는 보이지 않고, 억지로 돌려도 거부합니다 (예: 강의 목록 SQL 주입은 사용자 웹에만).
  • 보고서에는 주소와 함께 역할이 찍힙니다. localhost:3000 만 적혀 있으면 나중에 어디였는지 모릅니다.
  • 역할은 프로젝트 팩의 PROJECT["roles"] 에, 모듈 쪽은 META["roles"] 에 적습니다.

서버 안쪽은 어디까지

  • 대시보드가 직접 보내는 것은 HTTP 요청뿐입니다. SSH 로 들어가 명령을 대신 실행하지 않습니다 — 그렇게 만들면 범위 검사가 닿지 않는 원격 실행 도구가 됩니다.
  • 서버 설정 점검은 서버 명령 출력 읽기 도구로 받습니다. sudo --version·ss -tlnp 결과를 붙여 넣으면 버전과 열린 포트를 정리하고 기준에 못 미치는 것을 결과로 만듭니다. 요청은 보내지 않습니다.
  • 비밀번호·키가 섞인 출력은 붙여 넣지 마세요. 붙여 넣은 글은 결과의 근거로 DB 에 남습니다.

표면

  • 엔드포인트(회색 줄) 아래에 그 주소의 파라미터가 놓입니다. 위치는 쿼리(URL ?뒤) · 폼 본문(POST) 입니다.
  • 출처: link 페이지 링크, form 폼 입력칸, js 스크립트 안 /api 경로, import 붙여 넣은 목록. 다른 도구(Burp·katana 등)로 모은 URL 은 URL 목록 가져오기 모듈에 붙여 넣으면 됩니다.
  • 판정은 지점 점검 모듈마다 따로 붙습니다. 마우스를 올리면 근거(보낸 요청·응답 발췌)가 보입니다. 취약 넣은 값이 그대로 돌아옴(후보) · 잠재 돌아오긴 하는데 바뀜(필터 있음, 다른 패턴으로 더 볼 곳) · 안전 돌아오지 않음.
  • 발견 값은 수집할 때 그 칸에 들어 있던 값입니다(링크의 ?target=1 의 1, 숨은 입력칸의 값, 체크박스 value 의 yes 등). 한 파라미터를 점검할 때 같은 요청의 나머지 파라미터를 이 값으로 채워 정상 요청 모양을 유지합니다. 비밀번호·토큰처럼 보이는 이름은 값을 저장하지 않습니다.
  • 점검한 뒤: 취약은 결과 탭에 쌓이고(같은 건 갱신), 잠재는 표면 탭에만 남아 다른 패턴으로 더 볼 곳으로 표시됩니다. 판정 칩을 누르면 그 판정에 쓴 요청·응답 원문이 열립니다.
  • POST 지점은 기본으로 보내지 않습니다. 폼을 실제로 제출하면 글·데이터가 저장될 수 있어서, 모듈 입력칸에 POST 를 넣을 때는 테스트 계정·테스트 행에서만 씁니다.
  • 수집 지점 비우기는 지점과 판정만 지웁니다. 결과 탭의 결과는 남습니다.

대상

  • 대상은 프로젝트 하나에 묶입니다. 프로젝트마다 허용 범위가 위에 보입니다.
  • 대상을 지우면 그 대상의 실행 기록과 결과도 함께 지워집니다.

모듈

  • 범용 모듈은 모든 대상에, 프로젝트 전용은 그 프로젝트 대상에만 보입니다.
  • 태그는 그 모듈이 다루는 ATT&CK 전술·기법입니다. 수동(읽기) 은 응답만 읽고, 능동 은 요청을 더 보내 실행 전 확인이 필요합니다.
  • 아래 최근 실행에 15개까지 남고, 실패하면 이유도 보입니다. 불러오지 못한 모듈은 맨 위 상자에 뜹니다.

ATT&CK

  • 14개 전술이 공격 진행 순서로 놓입니다. 칸 하나가 모듈이 다루는 기법 하나입니다.
  • 주황 칸은 지금 대상에서 발견된 기법입니다(오탐 제외). 칸을 누르면 MITRE 설명 페이지가 열립니다.

시나리오

  • 미확인·확인됨 결과를 전술 순서로 묶은 초안입니다. 순서만 잡아 주고, 무엇이 무엇으로 이어지는지는 팀이 판단합니다.
  • 보고서는 오탐을 뺀 결과를 심각도 순으로 담습니다.

요청 기록

  • 모듈이 보낸 모든 요청과 받은 응답이 남습니다(패킷이 아니라 HTTP 요청·응답 단위). 줄을 누르면 원문, 노란 표시는 점검 표식입니다.
  • 모듈 탭 '최근 실행'의 요청 N개 보기, 결과 상세의 보낸 요청 · 받은 응답 보기, 표면 판정 칩에서 바로 들어옵니다.
  • Cookie · Authorization 같은 인증 값과 응답의 Set-Cookie 값은 *** 로 남깁니다. .env 처럼 비밀이 섞일 응답은 본문을 남기지 않습니다.
  • 보고서(Markdown·JSON)에도 결과마다 요청 원문과 응답 앞부분이 들어갑니다.

로그인한 상태로 점검

  • 대상 탭의 인증 헤더에 Cookie: ... 나 Authorization: Bearer ... 를 넣으면 그 대상 주소로 가는 요청에만 붙습니다. 다른 주소로는 나가지 않습니다.
  • 값은 이 PC 의 instance/ DB 에만 있고 화면·기록에는 이름만 보입니다. 테스트 계정 토큰만 넣습니다.

요청 간격 · 한도

  • 실행 하나에서 요청 사이 {{ config.DELAY_MS }}ms 를 쉬고, {{ "{:,}".format(config.MAX_REQUESTS) }}개를 넘으면 멈춥니다. 공유 서버를 덜 괴롭히기 위해서입니다.
  • 바꾸려면 실행 전에 환경변수 DASH_DELAY_MS · DASH_MAX_REQUESTS 를 줍니다.
  • 대시보드 자신(127.0.0.1:{{ config.SELF_PORT }})은 대상이 될 수 없습니다. 자기 폼을 점검하면 실행·삭제가 실제로 일어나기 때문입니다. 시험은 연습용 대상(python demo_target.py → 127.0.0.1:5051)으로 합니다.

범용 모듈과 프로젝트 팩

구분위치넣는 것
범용modules/어느 서비스에나 쓰는 점검. 특정 주소·경로·계정은 넣지 않음
프로젝트 팩projects/<id>/__init__.pyPROJECT = 이름 · 허용 범위(scope) · 설명

다른 서비스를 점검하게 되면 projects/ 아래에 폴더를 하나 만들면 됩니다. 앱 코드는 고치지 않습니다.

모듈 만들기

단계 (META stage)run 모양예
표면 수집 collectrun(target, params) → [Point]modules/surface_crawl.py
지점 점검 proberun(target, points, params) → [Check]modules/reflection_check.py
대상 점검 check(기본)run(target, params) → [Finding]modules/_template.py

SQLi·XSS·경로 조작처럼 유형별 점검은 지점 점검(probe)으로 만들면 표면 수집 결과를 그대로 받아 씁니다. 값 넣어 보내기는 probe.send(point, 값), 반사 판정은 probe.judge_reflection() 을 씁니다. 판정 기준(패턴)만 바꾸면 됩니다.

  1. modules/_template.py 를 복사해 범용이면 modules/, 전용이면 projects/<id>/modules/ 에 둡니다. 파일 이름이 _ 로 시작하면 등록되지 않습니다.
  2. META 를 채우고 run(target, params) 에서 Finding 목록을 돌려줍니다.
  3. 대시보드를 다시 실행하면 모듈 탭에 나타납니다. 오류가 있으면 모듈 탭 맨 위에 이유가 뜹니다.
META = {
    "id": "xss_reflect",            # 전체에서 하나
    "name": "XSS 반사 확인",
    "category": "입력 검증",
    "kind": "active",               # passive / active
    "attack": [{"tactic": "TA0001", "technique": "T1190", "name": "..."}],
    "description": "한 줄 설명",
    "params": [{"name": "path", "label": "경로", "default": "/"}],
}

def run(target, params):
    r = fetch(target.url + params["path"])   # 요청은 fetch 로만
    return [Finding(title="...", severity="medium", location=r.url,
                    evidence="요청·응답 근거", recommendation="조치")]
  • 요청은 core.fetch 로만 보냅니다. 범위 검사와 리다이렉트 차단이 여기서 걸립니다. 기존 도구를 감싸면 대상 주소를 scope.ensure_in_scope(url) 로 먼저 검사합니다.
  • 근거에 쿠키 값·토큰·.env 내용 같은 비밀값을 남기지 않습니다.
  • 심각도는 critical · high · medium · low · info 중 하나입니다.

안전장치

  • 대시보드는 127.0.0.1 에서만 열립니다. 다른 이름(Host)으로 들어온 요청과, 다른 사이트가 몰래 보낸 POST(CSRF)는 거부합니다.
  • 모듈 실행 중 요청은 그 대상 프로젝트의 허용 범위 밖으로 나가기 전에 막힙니다.
  • 모듈 하나가 깨져도 나머지는 뜨고, 실패도 실행 기록에 남습니다.

아직 없는 것

  • 유형별 페이로드 모듈(SQLi·XSS·경로 조작 등)과 오류·시간·길이 차이 판정기 — 담당 팀원이 지점 점검 틀로 추가.
  • 오래 걸리는 실행을 뒤에서 돌리고 진행률 보기, 실행 간 비교, 로그인 토큰 자동 갱신.
  • 타임라인, CVE 탭, Word/PDF 보고서.
